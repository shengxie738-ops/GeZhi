# 102V12 reliability and safety repair plan

## Approved scope
On 2026-10-02 the project owner requested a new 102V12 branch and repairs to all five priority categories from the preceding GeZhi audit. Work stays in dot's existing cloud workspace. Codex Cloud, Gitea and RAGFlow are excluded. Base commit: 041002e90ffd03344fd40ec31c06b3da9823cd1c.

## Outcome
Existing teaching workflows must report only server-confirmed success, protect identities and assessment content, preserve exam work across retries, distinguish operational features from demonstrations, and never execute untrusted code in the application security context.

## Work packages and acceptance
- [x] Backend authorization: verified token identity, self/assigned-student ownership, restricted teacher signup, protected history/configuration/evaluation routes. Anonymous, invalid-token and cross-user negative tests.
- [x] Assessment integrity: student-safe question schemas, validated exam publication/time windows, idempotent resume/finalize, durable answer lifecycle, scoped judge access. Retry and missing-resource tests.
- [x] Frontend reliability: no implicit mock success after API failure; user-visible unsaved/error state; exam switching and autosave; complete logout/expiration cleanup. 403/network/error and two-exam regressions.
- [x] Teaching operations: no invented students, attendance, delivery or saved courses. Use existing authorized APIs where available; otherwise explicitly identify unsupported capability, rather than inventing a new subsystem.
- [x] Execution/rendering boundaries: remove host/main-thread untrusted execution; fail closed with explicit unavailable status until a separately isolated execution service exists. Unavailable must not be scored as incorrect. Central safe rendering with no unsanitized fallback.
- [x] Independent review: inspect combined changes and cross-package contracts; fix material findings.
- [x] Verification: focused regression tests, existing permitted suites, frontend build, safe full-stack HTTP smoke using isolated synthetic data. Browser acceptance where supported; clearly distinguish stages that could not run.

## Constraints and compatibility
No real external AI/services, credentials, production data writes, or changes to uploaded/raw database baselines. Preserve existing API/UI behaviors unless they are the documented defect. No unrelated redesign or replacement framework. No remote push, merge, or deployment is part of this request. Existing excluded integration failures remain separately identified.

Teacher access must use trusted assignment data, not self-editable class labels. Empty assignments fail closed; onboarding/configuration implications must be documented. If no secure code runtime is available, disabled execution is an intentional capability reduction, not a claim of a completed isolated runner.

## Verification focus
401/403 are never success; late or duplicate exam actions cannot erase/finalize twice; different users/exams cannot share state; empty teacher queues stay empty; sanitizer/runtime failures are explicit and safe. Changes to protected endpoints must be reflected in frontend token handling and real HTTP tests, not only source-text assertions.
